# Private GitHub deployment design

## Intent

Allow the single Arfeen Cloud administrator to connect a private GitHub repository, choose a branch, and deploy or redeploy it through the existing Applications dashboard. Keep repository credentials on the Ubuntu server and preserve the existing Docker image build and deployment model.

## Goals

- Connect GitHub with a fine-grained personal access token limited to selected repositories and read-only repository contents.
- Validate the token and list repositories and branches the token can access.
- Save a repository and branch as an application's source so later dashboard redeploys fetch the same source.
- Keep credentials encrypted in the persistent application database and never include them in clone URLs, API responses, UI logs, or deployment records.
- Make the deployment flow visible: fetch source, detect framework, build image, start the replacement, and record success or failure.
- Continue supporting public GitHub URLs and ZIP uploads.

## Non-goals

- Automatic deploys on every push in this release.
- GitHub Actions runners or arbitrary workflow execution on the server.
- Private GitHub Enterprise hosts, organization policy administration, or multi-user access.
- Publicly exposing Arfeen Cloud to receive GitHub webhooks.

## Current project behavior

The Deploy modal accepts a public HTTPS GitHub URL or a ZIP. The FastAPI `/api/apps/github` endpoint clones the URL with `git clone`, detects the framework, builds a Docker image, and starts a container. The application record stores the source URL. Redeploy clones that URL again. There is no credential store, repository browser, branch selector, or deployment progress record for failed builds.

Arfeen Cloud is currently deployed behind Tailscale Serve, so GitHub cannot send an inbound webhook to it. Dashboard-triggered deploys work with the current private access model.

## Approaches considered

1. **Fine-grained personal access token with dashboard-triggered deployment (recommended).** The administrator creates a token limited to selected repositories with contents read permission. The dashboard validates it, browses accessible repositories and branches, and initiates builds. This fits the current single-admin and Tailscale-only setup. It requires protecting a long-lived credential on the server.
2. **GitHub App with signed push webhooks.** Installation-scoped credentials and push events provide a stronger long-term integration. It requires creating and hosting a GitHub App, a publicly reachable webhook endpoint, signature verification, and asynchronous deployment jobs. It does not fit the current private-only ingress without additional exposure.
3. **Self-hosted GitHub Actions runner.** A workflow can request deployment through a runner that polls GitHub outbound. This avoids inbound webhooks but gives repository workflow code a path to execute on the server, which is too broad for the first private-repository release.

The default for this design is approach 1. A later webhook integration can reuse the repository and deployment records.

## Design

### GitHub connection

Add a GitHub connection area under Settings with a token input, connection test, repository access summary, and disconnect action. Accept a fine-grained PAT and explain the minimum required permission: read repository metadata and contents for the selected private repositories. Do not return the saved token to the browser. On save, encrypt it with a dedicated `GITHUB_CREDENTIALS_KEY` application secret generated by the installer and persisted in `.env` with restrictive permissions. Require this key to remain stable across restarts and updates. Reject token values in logs and generic exception detail.

Add authenticated backend endpoints to test/save the token, list accessible repositories, list branches for a repository, and disconnect. Use GitHub's HTTPS API and validate repository owner/name values before requesting data. Bound pagination and response sizes. The connection response reports whether a credential is saved; it does not return an account name because GitHub's [authenticated-user endpoint](https://docs.github.com/en/rest/users/users#get-the-authenticated-user) does not support fine-grained personal access tokens.

### Deploy and redeploy flow

In the GitHub tab of Deploy, allow selecting a connected repository and branch. Keep the existing name, domain, environment variable, and ZIP flows. For public URLs, continue supporting URL-based deployment without a connection. A GitHub source record identifies repository owner/name and branch; credentials are resolved on the server at clone time.

Clone with an ephemeral credential mechanism so the token never appears in the repository URL or saved source. Preserve shallow clones. Share the same clone implementation between initial deployment and redeploy. On clone failure, show a sanitized GitHub error and retain diagnostic detail only after redacting credentials.

### Deployment pipeline state

Record deployment attempts, including failure status and a safe stage/message, for GitHub builds. The initial implementation may keep the request synchronous but should return clear stage-specific failures and avoid recording secrets or raw environment values. Do not delete the currently running container until the new image has built and the replacement can be started; use the existing rollback behavior where possible.

### Compatibility and migration

Keep existing public GitHub URL application records deployable. Existing ZIP applications are unchanged. Schema changes must be additive and safe for an existing SQLite database. The new credentials key must be generated for new installs and documented for existing installations; if missing, the connection UI should explain how to add it and restart the stack rather than silently storing a plaintext token.

## Security constraints

- Only the authenticated administrator may manage the GitHub connection or deploy private repositories.
- Tokens are encrypted at rest with a separate key and never echoed after saving.
- Clone operations use only HTTPS GitHub hosts and validated repository paths.
- Limit the recommended token to contents read access and specific repositories.
- Keep private repository names and build output behind the existing authenticated dashboard.
- Do not add an unauthenticated webhook endpoint in this release.

## Acceptance criteria

- The administrator can save and validate a fine-grained GitHub token.
- The UI lists authorized private repositories and branches.
- Deploying a selected repository and branch builds and starts the app using existing framework detection.
- Redeploy fetches the same selected branch without requiring the user to re-enter a token.
- Token storage, API responses, errors, logs, application source, and deployment history do not reveal the token.
- Public repository URL and ZIP deployment paths remain available.
- An existing installation can be updated without losing applications, deployment history, or files.

## Open implementation choices

- Whether to display deployment stage updates by polling or keep the first implementation request-based with explicit stage errors. Default: request-based to avoid adding a job queue before the current synchronous build flow needs one.
- Cryptography package and encryption format. Default: an authenticated encryption library with a dedicated 32-byte key, not the JWT signing secret.
