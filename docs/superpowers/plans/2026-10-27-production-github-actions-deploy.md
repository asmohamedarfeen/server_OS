# Production GitHub Actions Deployment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Automatically deploy the exact commit pushed to `main` onto the existing private Ubuntu Docker Compose server with protected data, serialized execution, health verification, and rollback.

**Architecture:** A repository-scoped GitHub Actions runner runs as `md` on the Ubuntu server and accepts only jobs labeled `arfeen-production`. A minimal workflow checks out the triggering commit and invokes a repository-owned Bash deployment script; that script locks production, snapshots code, synchronizes into `/home/md/arfeen-cloud` while excluding persistent paths, runs Compose, verifies the local endpoint, and restores the snapshot after failure.

**Tech Stack:** GitHub Actions, GitHub self-hosted runner, Bash, rsync, util-linux `flock`, Docker Compose, systemd.

**Spec:** `docs/superpowers/specs/2026-10-27-production-github-actions-deploy-design.md`

## Global Constraints

- Production deploys only from `main` or a manual dispatch of the workflow on `main`.
- The live Compose project remains `arfeen-cloud` at `/home/md/arfeen-cloud`.
- Never read into logs, replace, copy into a backup, or delete `/home/md/arfeen-cloud/.env`.
- Never replace or delete `/home/md/arfeen-cloud/storage`, `arfeen_data`, or `deploy_workspace`.
- Do not run `docker compose down`, Docker prune commands, or volume deletion commands.
- The workflow has `contents: read`, no production secrets, no pull-request trigger, and `cancel-in-progress: false`.
- The runner is repository-scoped to `asmohamedarfeen/server_OS`, runs as `md`, and has the custom `arfeen-production` label.
- Use the runner package/version and checksum generated by GitHub's repository Settings page at installation time; do not hard-code a stale runner download.
- Promote the existing `feat/private-github-deploy` branch to `main` only after local verification and runner installation.

## Review Focus

- **Protected paths during sync and rollback:** tests must prove `.env` and `storage/` contents survive both success and failure unchanged.
- **Failed build or startup:** tests must prove the old source is restored and rollback Compose is attempted before a non-zero exit.
- **Concurrent jobs:** tests must prove a second process cannot enter the deployment while the lock is held.
- **Wrong checkout:** tests must prove an Actions job whose checked-out `HEAD` differs from `GITHUB_SHA` fails before touching production.
- **Health-check timeout:** tests must prove repeated failed probes cause rollback and a failed workflow instead of reporting success.
